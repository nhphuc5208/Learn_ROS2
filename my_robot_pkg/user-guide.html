Component-by-component user guide

Workspace ~/ros2_ws · ROS 2 Jazzy · Gazebo Harmonic · 3 packages: my_robot_interfaces, my_robot_pkg, my_robot_description

Each section covers: what it does, how to run it, parameters, topics/services, and how to tell it works. Click the Copy button on any command block to copy it.

0. Build & source — do this first

cd ~/ros2_ws
colcon build --symlink-install
source install/setup.bash
  • Every new terminal must run source ~/ros2_ws/install/setup.bash (or the sws alias). To make it automatic, uncomment the source ~/ros2_ws/install/setup.bash line in ~/.bashrc.
  • Thanks to --symlink-install, edits to .py, .yaml, .xacro and launch files take effect immediately. Rebuild only when you add a new file, add an entry point in setup.py, edit package.xml, or edit a .msg.
  • Build a single package: colcon build --symlink-install --packages-select my_robot_pkg
List every runnable program: ros2 pkg executables my_robot_pkg — you should see 9: machine_status_publisher, motor_service, patrol_node, qos_pub, qos_sub, square_driver, temp_monitor, temp_publisher, temp_subscriber.

5-minute quick demo

To see the final result right away: one command starts Gazebo + SLAM + Nav2 + RViz2 + the patrolling robot.

ros2 launch my_robot_pkg patrol.launch.py

Wait about 20–30 seconds: Gazebo shows the factory, the map gradually appears in RViz2, and the robot drives through 4 waypoints on its own. The terminal prints [OK] Reached waypoint 1 (lap 1)… Stop with Ctrl+C.

temp_publisher Day 2

What it does: simulates an air-compressor temperature sensor, publishing random values between 55 and 95 °C at a steady rate.

ros2 run my_robot_pkg temp_publisher
ros2 run my_robot_pkg temp_publisher --ros-args -p rate_hz:=5.0 -p machine_id:=AC-07
ParameterDefaultMeaning
rate_hz2.0Messages per second
machine_idAC-01Machine name printed in the log

Publishes: topic /compressor/temperature of type std_msgs/msg/Float32.

Check:

ros2 topic echo /compressor/temperature
ros2 topic hz /compressor/temperature      # should be ≈ rate_hz

temp_monitor Day 2

What it does: listens to the temperature from temp_publisher, prints OK or an OVERHEAT warning above the threshold, and counts the alarms.

ros2 run my_robot_pkg temp_monitor --ros-args -p threshold:=75.0
ParameterDefaultMeaning
threshold85.0Alarm threshold (°C). Can be changed while running.
InterfaceNameType
Subscribe/compressor/temperatureFloat32
Service/temp_monitor/reset_alarmstd_srvs/srv/Trigger — resets the alarm counter to 0
# change the threshold at runtime
ros2 param set /temp_monitor threshold 90.0
ros2 param get /temp_monitor threshold
# reset the counter
ros2 service call /temp_monitor/reset_alarm std_srvs/srv/Trigger

Works when: the log shows OVERHEAT 88.1 C (> 75.0) - alarm #3; after a reset, the next alarm is alarm #1.

temp_subscriber Day 2

What it does: a minimal subscriber for practice. Listens on /temperature (a different topic from temp_publisher!) and warns above 30 °C.

ros2 run my_robot_pkg temp_subscriber
# in another terminal, feed it values:
ros2 topic pub -r 1 /temperature std_msgs/msg/Float32 "{data: 35.5}"
Running it alongside temp_publisher receives nothing because the topic names differ. To connect them: ros2 run my_robot_pkg temp_subscriber --ros-args -r temperature:=compressor/temperature (remap).

motor_service Day 2

What it does: a service server that switches a motor on/off (it only stores the state and logs it).

ros2 run my_robot_pkg motor_service
ros2 service call /set_motor std_srvs/srv/SetBool "{data: true}"    # ON
ros2 service call /set_motor std_srvs/srv/SetBool "{data: false}"   # OFF

Works when: the call returns success=True, message='Motor is ON'.

machine_status_publisher Day 2

What it does: publishes machine status with the custom message my_robot_interfaces/msg/MachineStatus (temperature, pressure, running) once per second.

ros2 run my_robot_pkg machine_status_publisher --ros-args -p machine_id:=MACHINE_03
ros2 topic echo /machine_status
ros2 interface show my_robot_interfaces/msg/MachineStatus

Parameter: machine_id (default MACHINE_01). About 10% of the time is_running = false to simulate a stopped machine.

qos_pub / qos_sub Day 3

What it does: demonstrates the QoS trap — when a publisher and subscriber have "incompatible QoS" there is no error, just silence.

ros2 run my_robot_pkg qos_pub --ros-args -p reliability:=best_effort
ros2 run my_robot_pkg qos_sub --ros-args -p reliability:=reliable      # receives NOTHING
ros2 topic info /qos_demo/data -v                                       # compare the Reliability column
PublisherSubscriberResult
best_effortreliableNothing received — sub prints a warning every 2 s
reliablebest_effortWorks normally
reliablereliableWorks normally

Quicker way: use qos_demo.launch.py.

square_driver Day 5

What it does: publishes /cmd_vel so the robot in Gazebo drives a square. It reads /odom to know when it has covered each edge / turned 90° (closed loop), so it ends up close to the starting point.

Start first: sim.launch.py. Do not run it together with teleop or Nav2 (they fight over /cmd_vel).

ros2 launch my_robot_description sim.launch.py rviz:=true          # terminal 1
ros2 run my_robot_pkg square_driver --ros-args -p use_sim_time:=true   # terminal 2
# 1.5 m square, 2 laps, faster:
ros2 run my_robot_pkg square_driver --ros-args -p use_sim_time:=true \
    -p side:=1.5 -p laps:=2 -p linear_speed:=0.5
ParameterDefaultMeaning
side2.0Side length (m)
linear_speed0.3Max forward speed (m/s)
angular_speed0.6Max turn rate (rad/s)
laps1Number of laps
use_sim_timefalseAlways set to true when running with Gazebo

Works when: the log shows Finished edge 1/4 … Square complete!, then ros2 topic echo /odom --once gives x, y close to 0 (measured: ~2 cm off).

patrol_node Day 7

What it does: the robot's "supervisor". Sends each patrol waypoint to Nav2 in turn (action navigate_to_pose), logs each arrival, and loops forever. A waypoint that fails is retried up to max_retries times, then skipped.

Usually not run on its own — use patrol.launch.py. To run it separately (while nav.launch.py is running):

ros2 run my_robot_pkg patrol_node --ros-args -p use_sim_time:=true \
    --params-file ~/ros2_ws/src/my_robot_pkg/config/patrol.yaml
ParameterDefaultMeaning
waypoints4 pointsFlat list [x, y, yaw, x, y, yaw, …] in the map frame
frame_idmapFrame of the waypoint coordinates
max_retries2Retries per waypoint before skipping it
InterfaceNameUse
Service/patrol/enable (SetBool)false = cancel the goal, robot stops immediately; true = continue to the current waypoint
Topic/patrol/status (String)GOING 2 lap 1, REACHED 2 lap 1, SKIPPED 3
Action client/navigate_to_poseProvided by Nav2
ros2 service call /patrol/enable std_srvs/srv/SetBool "{data: false}"   # stop
ros2 service call /patrol/enable std_srvs/srv/SetBool "{data: true}"    # resume
ros2 topic echo /patrol/status

tf_demo.launch.py Day 3

What it does: builds a TF tree by hand (no URDF yet): odom → base_footprint → base_link → lidar_link / camera_link, and opens RViz2 with rviz/day3.rviz.

ros2 launch my_robot_pkg tf_demo.launch.py
ros2 launch my_robot_pkg tf_demo.launch.py rviz:=false
ros2 run tf2_ros tf2_echo base_link lidar_link     # x=0.10, z=0.15
ros2 run tf2_tools view_frames                      # creates frames_xxx.pdf

patrol.launch.py Day 7 · full system

Starts everything: Gazebo + bridge + SLAM (or AMCL) + Nav2 + RViz2, then after 20 seconds starts patrol_node (waiting for Nav2 to be ready).

ros2 launch my_robot_pkg patrol.launch.py
ros2 launch my_robot_pkg patrol.launch.py headless:=true        # no Gazebo GUI, lighter on resources
ros2 launch my_robot_pkg patrol.launch.py \
    map:=$HOME/ros2_ws/src/my_robot_description/maps/factory_map.yaml   # use a saved map
ArgumentDefaultMeaning
map(empty)Empty = SLAM builds the map as it goes. A path = AMCL on that map
rviztrueOpen RViz2
headlessfalsetrue = Gazebo runs in the background, no window
With map:=…, AMCL does not know where the robot is yet: in RViz2 click 2D Pose Estimate, click on the robot's position (origin 0,0 in the middle of the factory) and drag in the direction it faces. Otherwise patrol will keep reporting failures.

Works when (verified): the log shows [OK] Reached waypoint 1..4 (lap 1) → ===== Starting lap 2 =====.

Obstacle-avoidance exercise: while the robot is running, drop a box in its path:

ros2 launch my_robot_description spawn_obstacle.launch.py x:=4.0 y:=2.0

Launch files in my_robot_description

display.launch.py Day 4

What it does: shows the robot in RViz2 with no physics. Starts robot_state_publisher + a joint slider window + RViz2.

ros2 launch my_robot_description display.launch.py
ros2 launch my_robot_description display.launch.py use_arm:=true    # with the revolute arm
ros2 launch my_robot_description display.launch.py gui:=false       # no sliders
ArgumentDefaultMeaning
use_armfalseAdds an arm_link that rotates -45°…+90° (exercise)
guitrueOpen joint_state_publisher_gui

Works when: you see a blue box, 2 black wheels, a LiDAR on top and a grey camera at the front. Dragging the left_wheel_joint slider turns the wheel around its horizontal axis. With use_arm:=true, the arm_joint slider stops exactly at its limits.

slam.launch.py Day 6

What it does: sim + SLAM Toolbox + RViz2 (fixed frame map) to build a map by driving manually.

ros2 launch my_robot_description slam.launch.py                 # terminal 1
ros2 run teleop_twist_keyboard teleop_twist_keyboard            # terminal 2: drive slowly around the factory

Arguments: rviz (true), headless (false).

Save the map once all 4 walls + 2 machines are visible:

cd ~/ros2_ws/src/my_robot_description/maps
ros2 run nav2_map_server map_saver_cli -f factory_map
# creates factory_map.pgm + factory_map.yaml
cd ~/ros2_ws && colcon build --symlink-install --packages-select my_robot_description

nav.launch.py Day 6

What it does: sim + (SLAM or AMCL) + Nav2 + RViz2. You set a goal; the robot plans a path and drives there.

# Mode 1: no prior map needed (SLAM maps as it goes)
ros2 launch my_robot_description nav.launch.py

# Mode 2: localize on a saved map (AMCL)
ros2 launch my_robot_description nav.launch.py \
    map:=$HOME/ros2_ws/src/my_robot_description/maps/factory_map.yaml

In RViz2:

  1. (Mode 2 only) Click 2D Pose Estimate → click on the robot's position and drag in the direction it faces.
  2. Click Nav2 Goal (or 2D Goal Pose) → click where you want to go and drag to set the heading.
  3. The robot plans a path (colored line) and drives it, going around the 2 machines.

Send a goal from the command line (no clicking):

ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 4.0, y: 4.0}, orientation: {w: 1.0}}}}"

Exercise: put a goal inside a wall → read the errors in the terminal (the planner reports no valid path found, bt_navigator reports Goal failed).

Do not run teleop together with Nav2 — both fight over /cmd_vel and the robot jerks.

Config files — what to edit where

my_robot_interfaces/msg/MachineStatus.msg Day 2

string machine_id
float32 temperature
float32 pressure
bool is_running

To add a field: edit the file → colcon build --packages-select my_robot_interfaces → source install/setup.bash. (.msg files always need a rebuild.)

urdf/my_robot.urdf.xacro and urdf/gazebo.xacro Days 4–6

All dimensions are at the top of my_robot.urdf.xacro:

PropertyValueNotes
base_len / base_wid / base_hei0.40 / 0.30 / 0.12Body size (m)
base_mass8.0kg — too small and the robot shakes or tips over
wheel_radius / wheel_width0.06 / 0.04DiffDrive picks these up automatically
wheel_sep0.34Distance between the wheels. Exercise: change to 0.5 → wider robot
base_z_off0.03Ground clearance. Do not set 0 — the body touches the floor and the robot cannot turn

gazebo.xacro holds the Gazebo-only parts: wheel friction, the DiffDrive plugin (takes /cmd_vel, publishes /odom), JointStatePublisher, the LiDAR (gpu_lidar, 360 rays, 0.15–12 m), a 640×480 camera, and the IMU.

The wheel collision is a sphere (the visual is still a cylinder). With a cylinder, Gazebo makes the wheel touch the floor at its inner edge, so odom is 13% off when turning and the SLAM map gets skewed.

worlds/factory.sdf Day 5

14 × 12 m factory: walls at x = ±7, y = ±6. machine_1 at (2.5, 1.5), machine_2 at (-2.0, -2.5). The robot starts at (0, 0).

To add a fixed obstacle: copy a <model name="machine_2">…</model> block and change its name and <pose>x y z roll pitch yaw</pose>.

Do not remove the plugins at the top of the file. Without gz-sim-sensors-system, /scan and the camera produce no data.

Common errors

SymptomCheck / fix
Package 'my_robot_…' not foundNot sourced: source ~/ros2_ws/install/setup.bash
No executable foundNot rebuilt after adding an entry point: colcon build --symlink-install
Robot does not move when pressing keys1) Does ros2 topic echo /cmd_vel show values? 2) Does gz topic -e -t /cmd_vel? Missing at step 2 means a bridge problem
Gazebo is black / crashesUse headless:=true
Patrol keeps printing Waiting for Nav2 action server...Nav2 is not up: ros2 lifecycle get /bt_navigator; look for red errors in the launch terminal

Everything acts strange after many runsClean up hung processes (commands below)
pkill -f gz; pkill -f "ros2 launch"; pkill -f rviz2
rm -rf /dev/shm/fastrtps* /dev/shm/sem.fastrtps* 2>/dev/null
cd ~/ros2_ws && rm -rf build install log && colcon build --symlink-install && source install/setup.bash
